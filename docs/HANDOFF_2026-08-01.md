## Stable crawler decisions

### Identity and authority

A `games` row is one Bughouse board, not the two-board match. Chess.com's board
UUID is canonical. Public monthly archives are authoritative; a callback-only
board is upgraded if it later appears publicly. Raw payloads and identifiers
remain losslessly retained.

### Eligibility

The intended threshold is inclusive at 2000 inside an exact one-calendar-year
window. Seeds are not exempt. Only public ratings and timestamped callback PGN
ratings qualify. Stored games remain when a player becomes dormant. The
qualification reconciliation is complete, and the current cohort is anchored
to the fixed inclusive evaluation window with zero invariant violations.

### Completion and terminal outcomes

For migration-0003 completions, only months in the latest authoritative full
archive manifest govern lifetime completion. Current-month maintenance cannot
clear or block that result. An unavailable manifest month is a recorded
terminal outcome; an unavailable archive list is a different outcome and does
not claim a completed lifetime crawl.

### Annual partner probing

The version-2 choice minimizes the BLAKE2 hash of:

```text
sampler-version | normalized-username | calendar-year | board-uuid
```

The choice is frozen in `partner_year_samples`, including for a partial current
year. Probe jobs remain globally de-duplicated by board UUID. The public
opponent graph measured before conversion was connected; annual callback probes
remain a low-cost safeguard against hidden partner-only components.

### Serial HTTP and interruption

There is one synchronous request in flight across both Chess.com hosts. The
client waits at least 100 ms plus jitter between completed requests, identifies
the operator, honours `Retry-After`, and backs off on network failures, 429s,
and 5xx responses. Durable jobs and expiring leases make interruption resumable.
Five consecutive job errors stop the worker by default. `Ctrl-C` and `SIGTERM`
record graceful stopped runs.

### Opening-tree architecture/prototype update — 3 August 2026

The next architecture slice described above is now complete. A format-neutral
immutable crawler adapter, compact SQLite baseline, prefix-interval packed trie
with sorted postings, compressed bitmap comparator, exact-prefix query readers,
validators, and atomic publication pointer were implemented with TDD. Full
shape and representative evidence is in
[`OPENING_TREE_ARCHITECTURE_PROTOTYPE_2026-08-03.md`](OPENING_TREE_ARCHITECTURE_PROTOTYPE_2026-08-03.md).

The selected format is the packed interval trie with sorted White/Black ordinal
postings. The revised production policy excludes non-checkmate games of six
plies or fewer and retains 431 genuine short checkmates. It yields 6,516,478
games, 11,625,223 logical nodes, and 96,570,295 relational memberships. The
revised projections are about 3.23 GiB packed and 5.38 GiB SQLite. The full index
was deliberately not built. The representative builders retain Python objects
and therefore cannot be used for the full corpus until a streaming/external-
sort writer passes the 4 GiB peak-RAM gate and reliable temporary/write-
amplification measurement.

The agreed next product slice is a local vertical explorer. A localhost service
will memory-map a representative packed artifact, and a configuration-gated
`bughouse-chess` route will query bounded node neighborhoods instead of loading
the artifact into JavaScript memory. The leading prefetch design targets five
plies but enforces hard node and encoded-byte budgets, always includes immediate
children, prioritizes deeper high-support continuations, and returns explicit
frontiers for later refill. A literal root-to-depth-five response would contain
about 97,057 nodes and is therefore not an acceptable default.

1. Implement the `short_non_checkmate` adapter outcome with TDD, retaining short
   checkmates and reporting deterministic policy counts.
2. Implement the selected packed format with a streaming/external-sort writer;
   compact the metadata component and repeat the representative benchmark under

   correction, publication, and rollback gates.
3. Build the memory-mapped local service and local Next.js route against the
   representative artifact. Compare per-move, fixed-depth, and adaptive budgeted
   neighborhood fetching with client caching and frontier refill.
4. Only after the writer gates pass, build and validate the full immutable local
   derived version from a checked raw snapshot and swap it into the same service.

5. Run the first routine permanent-tracking monthly refresh under supervision;
